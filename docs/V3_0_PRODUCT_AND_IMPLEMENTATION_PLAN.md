# PDFDocuEdit Pro V3.0 功能、UI 與效能計劃書

**規劃基線：** v2.5.14（2026-09-28）

**首發平台：** Windows x64；沿用英文介面、現有淺色／深色主題及本機處理模式。

**文件性質：** 實作規格與驗收準則；本文不代表功能已完成或已有 V3.0 發布日期。

## 1. 產品目標與版本邊界

V3.0 的核心是**提升現有 Tools，並讓它們透過可重用的工作流接力**。使用者應可從目前 PDF、資料夾或工具結果開始，組合相容步驟、預覽輸出、執行、檢查結果及重試失敗項目，而毋須在多個對話框反覆輸入同一批檔案和頁碼。

本版本須同時達成三件事：

1. **少重複操作：** 搜尋結果、選頁及輸出檔案成為下一工具的輸入；現有 Tools 仍可獨立使用。
2. **操作可預期：** 每步顯示來源、選項、輸出和錯誤；預設保留原檔，執行前先檢查衝突。
3. **維持速度：** 開檔、縮圖及大量檔案清單不能因工作流功能而退步；所有來源探測與文件處理須避免阻塞 GUI。

OCR、雲端 AI、自由節點流程圖、任意 Python 腳本、背景自動續跑及整個主視窗重寫均不列入 V3.0。OCR 保留為現有獨立工具。工作流首發以**有文字 layer 的 PDF**及 Windows 實際工作流程驗收。

目前已知的使用者證據是：主要處理有文字 layer 的 PDF、OCR 使用率低，並希望優先改善現有 Tools 的交接、UI 和效能。**情境 A／B 的使用頻率尚未核實**；下述功能優先序是待 M0 驗證的產品假設，不能宣稱代表所有使用者。

## 2. 現況與要解決的問題

| 現有能力 | V3.0 要解決的斷點 |
| --- | --- |
| Deep Search 可搜尋資料夾並匯出 CSV；文件內搜尋結果已有頁面操作 | 跨檔命中結果不能作為可保存、可核對的多文件頁面集合，亦不能直接交給 Extract／Merge。 |
| Extract、Advanced Page Organizer、Merge、Compress、Compare、Analysis 均已存在 | 大部分由 `core/viewer.py` 的獨立對話框啟動；選項、結果及錯誤不能在工具之間可靠傳遞。 |
| `core/tasks.py` 提供背景任務和合作式取消；`ui/task_bar.py` 顯示單一任務 | 缺少整批工作的逐檔狀態、步驟進度、失敗重試和重開程式後的手動續跑。 |
| `core/io_atomic.py` 與部分 PDF 工具已有暫存寫入和檢查 | 仍須為整條工作流統一輸出衝突檢查、取消清理和來源不被覆蓋的規則。 |
| `ui/workspace.py` 有 Welcome／文件分頁，側欄、命令面板及主選單均有工具入口 | 高頻工作缺少一個可查看全程、切回文件又不會失去進度的工作區。 |

既有性能資料是歷史單次樣本，**不能直接視為 V3.0 基線**。例如 `docs/STARTUP_AND_OPEN_PERFORMANCE.md` 記錄 18,000 頁合成 PDF 的首次顯示、頁面模型及縮圖工作；`docs/MERGE_PERFORMANCE.md` 記錄 200 個檔案加入清單和合併的改善。第一階段必須在當前 HEAD 上重跑並記錄多次中位數。

### 2.1 M0 產品驗證關口

開發 Studio 前，收集至少 10 宗最近的實際 PDF 任務，逐宗記錄使用的 Tools、是否重複輸入檔案／頁碼、完成時間及錯誤；再以至少 3 宗真實任務量度現有操作與簡單可點擊原型的步驟數和完成時間。若能接觸其他目標使用者，另觀察 3 位使用者完成相同任務；若只有產品擁有人使用，改以兩週任務日誌補足，並在報告標明代表性限制。這是任務研究，不加入自動使用紀錄或上傳文件。

**M0 的決定：** 將實際頻率最高、且確實需要兩個以上 Tools 接力的兩條流程納入 V3.0。若本文情境 A 或 B 不在前兩位，替換該情境和內建範本；保留共用輸入、輸出與效能目標。若觀察不到有價值的多工具流程，先交付 Tool UX 與效能改善，暫不建 Studio。M0 完成前不開始通用適配層或 Studio 主畫面。

## 3. V3.0 使用情境與交付功能

以下 A／B 是目前候選情境；M0 驗證後須把實際入選的兩條流程及相應驗收案例更新到本節，才開始 M1。

### 3.1 情境 A：跨文件搜尋、選頁、交付

1. 使用者加入資料夾或多份 PDF，輸入一個或多個文字條件。
2. Deep Search 在背景執行；結果按文件顯示命中頁及片段，並可多選、移除誤中、調整頁序。
3. 使用者按 **Send to Workflow**，選擇 **Extract selected pages** 和 **Merge PDFs**；預覽每份來源對應的頁面及最終頁序。
4. 輸出一份新 PDF，以及 CSV 來源對照表（輸出頁碼、來源檔案、來源頁碼、命中條件）。從輸出頁面可於工作台返回來源頁。

此流程把現有搜尋、擷取及合併串起來。來源對照表是 V3.0 的新交付能力，方便日後追查文件來源。

### 3.2 情境 B：批次整理與交付檢查

1. 使用者加入多份 PDF，選擇原檔次序及是否合併；可選擇在合併後或逐檔壓縮。
2. 工作台先列出預計輸出、同名衝突、無法讀取檔案及需要密碼的檔案。
3. 執行後逐檔顯示狀態；輸出重新開啟檢查可讀性、頁數、檔案大小及現有 Analysis 可提供的警告摘要。
4. 使用者檢視結果，開啟輸出或匯出 CSV。壓縮後變大屬警告，不會被誤報為處理失敗。

### 3.3 現有工具的具體升級

| Tool | V3.0 改動 | 驗收結果 |
| --- | --- | --- |
| Deep Search | 結果多選、保存查詢設定、產生帶來源頁碼的結果集合；保留原有直接開檔和 CSV 匯出。 | 可從 20 份文字 PDF 的命中頁建立工作流輸入；來源改動後舊結果標示過期。 |
| Extract／Organizer | 接受工作流傳入的頁面集合，顯示來源及頁序；使用者仍可在套用前調整。 | 不須重新輸入頁碼；預覽和輸出頁數一致。 |
| Merge | 接受上一步的檔案集合和明確次序，顯示預計總頁數及輸出對照。 | 合併結果與預覽順序一致，並保留現有取消及檢查語義。 |
| Compress | 將現有設定作為可重用步驟；結果顯示壓縮前後大小與增減。 | 可對合併結果或逐檔結果執行，且不覆蓋來源。 |

Compare 的 CSV 差異摘要與批量版本配對列為 **V3.1 候選**；V3.0 保留現有 Compare，不把它納入首批工作流適配，避免分散核心流程的工程量。

### 3.4 工作流規則

工作流使用**線性步驟清單**，可加入、移除、調整相容步驟的次序和儲存範本。若 M0 確認 A／B，則只為五個現有核心操作建立適配：`Search text`、`Extract pages`、`Merge PDFs`、`Compress PDFs`、`Inspect output`；`Select pages` 是人工審核點，`Export report` 是共用輸出動作，不另建兩個通用 Tool adapter。沒有搜尋步驟時，`Select pages` 可從文件縮圖／Organizer 的選取開始。若 M0 選出其他流程，先更新這份操作清單及輸入／輸出契約，才進入 M1。

- Builder 只顯示與目前結果類型相容的下一步；不相容次序即時解釋原因，不能執行。
- `Search text` 沒有命中時，相關文件列為 **No match**，交由使用者決定排除或保留整份；不自動產生空 PDF。
- `Merge PDFs` 是多份輸入匯成一份輸出的步驟；執行前必須已確定來源順序。壓縮可選擇作用於每份文件或合併後結果，預覽會清楚顯示作用對象。
- 範本只保存步驟與工具選項，不保存檔案路徑、密碼或搜尋所得文件內容。搜尋字串只在使用者明確選擇 **Save query in template** 時本機保存；另有工作紀錄保存本次來源與狀態。
- 目前的兩個內建範本候選為 **Find → Extract → Merge** 和 **Combine → Compress → Inspect**；M0 若選出其他高頻流程，即以該流程替換候選範本。使用者可以另存自己的範本。

## 4. UI 規格

### 4.1 工作區與導覽

- 在現有 `DocumentWorkspace` 的中央 stack 加入 **Workflow Studio** 頁面，不把它偽裝成 `DocumentSession`。切到文件分頁再返回時，步驟、選頁和佇列仍在。
- Welcome 加入 **Create Workflow** 和最近使用範本；Tools 側欄與 `Ctrl+K` 命令面板加入相同入口。Deep Search、Organizer 等結果面板提供 **Send to Workflow**。
- Studio 的主要畫面由 **Sources／Steps／Preview & Run** 三區組成。選步驟時右區顯示該步選項、預計輸入／輸出及錯誤；執行後切換為逐檔結果和報告。
- 首頁預設先呈現兩個可直接使用的範本及 **Run once**；需要修改流程時才展開 Steps 編輯。獨立 Tools 的原有入口和操作路徑保持可見，使用者不必先學 Studio 才能完成日常工作。
- 在 960×640 視窗，三區改為可切換頁籤，不允許重要按鈕被水平裁切；深淺色、200% Windows 縮放、鍵盤焦點及可讀的狀態文字均須驗收。
- 主工具列只顯示一個精簡的工作流狀態入口；完整逐檔紀錄在 Studio。現有單一任務 `TaskBar` 仍服務其他 Tools，不承擔整批紀錄。

### 4.2 執行前預覽與任務狀態

**Preview** 必須列出輸入檔案數、選中頁數、步驟作用範圍、輸出名稱／資料夾、已存在的檔案及阻止執行的問題。新增檔案後先畫出快取／待檢查列，背景才讀取本機或 UNC 路徑 metadata，不得同步打開每份 PDF。

每個來源的狀態為 `Pending`、`Running`、`Completed`、`Warning`、`Failed`、`Needs review` 或 `Skipped`。`Cancel` 在安全檢查點停止；已完成檔案保留，未完成的暫存輸出清除。重新開啟程式只恢復清單，**不自動續跑**；使用者檢查後按 **Resume remaining** 或 **Retry failed**。

## 5. 工程設計與資料契約

### 5.1 工具與工作流引擎

只為 M0 選出的流程所需操作建立不依賴 Qt 對話框的**窄接口**，宣告穩定 `tool_id`、輸入／輸出類型、該操作的選項、進度／取消及輸出驗證函式。M0 先用所選首條流程中的兩個 Tool 驗證接口是否足夠，再加入其餘操作；V3.0 不建對外插件 API 或適配所有 Tools 的通用框架。獨立 Tool UI 和工作流共用核心操作；不得靠模擬按鈕點擊或互相開啟對話框執行。

內部資料類型：

| 類型 | 必備內容 |
| --- | --- |
| `DocumentSet` | 有序來源、顯示名稱、來源檔案識別資料；當前未儲存文件以執行時 snapshot 作輸入。 |
| `PageSelection` | 來源檔案、零基頁碼、顯示頁碼、選取次序及可選搜尋條件。 |
| `PdfSet`／`PdfOutput` | 暫存或已提交輸出、頁數、來源頁對照及輸出狀態。 |
| `FindingReport` | 每檔警告／錯誤、完成步驟、輸出路徑及可匯出摘要。 |
| `WorkflowSpec`／`RunRecord` | 有版本號的步驟及參數；本次來源、已確認的選頁、每步狀態、輸出對應和重試所需資料。 |

工具輸出須保留來源頁對照。磁碟來源以路徑、檔案大小及修改時間作快速識別，執行每份文件前重新開啟並檢查頁數；目前已開啟文件另檢查 `PdfEngine.revision`。使用者對搜尋／分析結果採取操作前若發現變更，即標示 **Needs review**，不能默默使用過期頁碼。執行期間每個 worker 擁有自己的 PyMuPDF document，不能在執行緒間同時共享同一 document。

### 5.2 輸出、安全與持久化

- 工作流預設輸出至使用者指定的**新資料夾**，絕不直接覆蓋來源。預覽階段處理重名來源和既存輸出；預設阻止衝突，使用者可修改輸出名稱後重試。
- 每個輸出先在目標目錄暫存，完成 PDF 開啟／頁數檢查後才提交。單個檔案的提交具原子性；整批多檔案不宣稱是單一原子交易。
- 搜尋擷取及合併之間的中間 PDF 放在任務專用暫存目錄，不作為正式輸出；取消／失敗後清理。續跑會重新計算未完成步驟，不依賴上次未提交的中間檔。
- 受密碼保護或有數位簽章的來源先在預覽標示。V3.0 自動工作流不處理加密來源，也不自動修改已簽署 PDF；使用者仍可使用原本獨立工具處理。工作紀錄不寫入密碼或文件文字。
- 範本及任務紀錄分別保存於使用者設定目錄，使用版本號和原子寫入。重啟時 `Running` 轉為 `Needs review`；續跑前確認來源和輸出仍存在。已完成項目不會重複寫出。

## 6. 效能與可靠性驗收

第一階段先在相同 Windows 機器、相同 fixture 上各跑至少五次，分開報告冷／暖快取中位數與 GUI 阻塞時間。須記錄：啟動至可互動、正常閒置開檔的 `queue_wait`、`time_to_first_page`、GUI completion 阻塞、首張與 12 張縮圖、18,000 頁 Organizer 初始化、200 檔加入 Studio、各步驟耗時及峰值記憶體。

| Gate | V3.0 驗收標準 |
| --- | --- |
| 現有開檔能力 | 100 頁及 18,000 頁 fixture 的 `time_to_first_page`、啟動可互動時間及峰值記憶體，不得比重新量度的 v2.5.14 基線中位數惡化超過 10%；異常須先分析再決定能否發布。 |
| 閒置開檔派送 | 移除仍存在的輪詢等待，正常閒置 `queue_wait` 目標低於 20 ms；GUI completion 阻塞目標低於 30 ms，與 wall-clock 首頁時間分開報告。 |
| 大批來源 | 加入 200 個本機 PDF 的 GUI 操作在 100 ms 內返回；斷線 UNC 路徑不得在 GUI 上同步 stat／open；清單使用按需 model。 |
| 背景執行 | 文件搜尋、來源檢查、合併、壓縮及驗證均可在運行時操作主視窗；取消只在安全檢查點生效，不宣稱能中斷 PyMuPDF 原生呼叫。 |
| 記憶體與資源 | 來源數／頁數增加不建立同比例 QWidget；PDF reader 限於其 worker、按任務生命週期釋放；取消及關閉無遺留檔案 handle／暫存輸出。 |

若未取得真實大型工作 PDF，報告須清楚標明合成 fixture 的限制；不把合成測試結果當成實際網路或影像密集 PDF 的保證。

## 8. 測試案例與發布驗收

以下第 1、2 項對應目前候選情境；若 M0 更換流程，須以同等規模的真實案例替換，並保留第 3–6 項的安全、相容與易用性驗收。

1. **主要流程：** 20 份含文字 PDF 搜尋兩組關鍵字、挑選命中頁、調整頁序、擷取及合併；核對輸出頁數、文字可搜尋、來源頁對照 CSV 及原檔不變。
2. **批次交付：** 200 份 PDF 加入清單、逐檔壓縮及檢查；包含同名檔、壓縮後變大、損壞檔和斷線路徑，結果逐檔準確，不因單檔失敗丟失先前成果。
3. **中斷恢復：** 執行中取消或強制結束程式，重開後顯示已完成／待覆核／失敗項目；手動續跑只處理未完成項，沒有正式輸出的半成品。
4. **來源失效：** 搜尋後變更來源、刪除輸出、切換有未儲存修改的文件；工作台清楚提示過期或重新 snapshot，不錯用舊頁碼。
5. **相容回歸：** 獨立 Deep Search、Organizer、Merge、Compress、Compare、Undo／Redo、文件開關及更新流程仍正常；執行完整 pytest、Ruff、source verification、Windows 打包及安裝後 smoke test。
